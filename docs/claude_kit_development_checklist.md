## 1. 작업 시작 전

- [ ] 요청 범위와 완료 기준을 정리했다.
- [ ] 요구사항이 모호한 부분을 먼저 확인했다.
- [ ] `CLAUDE.md`를 읽었다.
- [ ] 참고 문서 이정표에서 관련 문서를 읽었다.
- [ ] 변경 대상의 기존 구조와 사용처를 확인했다.
- [ ] 신규 API면 `spring-api-create`, 기존 API 변경이면 `spring-api-update`, 제거면 `spring-api-delete` Skill을 확인했다.

## 2. 설계·구현

- [ ] 기존 Controller → Service → 데이터 접근 구조를 유지했다.
- [ ] 프로젝트의 Java·Spring Boot·Gradle 버전을 따랐다.
- [ ] 프로젝트에서 사용하지 않는 JPA·MyBatis-Plus·QueryDSL·WebFlux·Swagger/OpenAPI를 임의로 추가하지 않았다. (데이터 접근은 2026-09-04부터 MyBatis)
- [ ] 클래스·메서드 역할과 필요한 파라미터·예외 주석을 작성했다.
- [ ] Service 레이어의 주요 흐름과 경고 로그를 작성했다.
- [ ] 비즈니스 예외가 있으면 프로젝트의 단일 예외 체계를 사용했다.
- [ ] 민감 정보와 자격 증명을 코드·설정·로그에 기록하지 않았다.

## 3. 테스트·검증

- [ ] 변경 계층에 대응하는 테스트를 작성하거나 수정했다.
- [ ] `./gradlew test`를 실행했다.
- [ ] 테스트 결과를 실제 출력으로 확인했다.
- [ ] 필요하면 Health Check·DB·외부 호출 등 변경된 경계를 별도로 검증했다.
- [ ] claude-kit Stop Hook의 컴파일·대응 테스트 결과를 확인했다.
- [ ] 테스트·빌드 실패를 남긴 채 완료 처리하지 않았다.

## 4. 문서·사람 검수

- [ ] API 경로·메서드·요청·응답이 바뀌면 README API 목록을 갱신했다.
- [ ] 프로젝트에서 관리하는 API 명세가 있으면 갱신했다.
- [ ] DB 테이블·컬럼·인덱스가 바뀌면 migration과 관련 문서를 함께 갱신했다.
- [ ] 설계 결정이나 구현 현황이 바뀌면 참고 문서를 갱신했다.
- [ ] claude-kit Review Hook의 검수 결과를 확인했다.
- [ ] Critical·High 위험 변경은 사람이 검수했다.
- [ ] 외부 부작용·권한·트랜잭션·동시성·삭제·시크릿 변경 여부를 직접 확인했다.
