# RAG 기본 개념과 활용 사례

이 문서는 RAG를 구현하기 전에 알아야 할 핵심 개념과 기업에서 RAG를 사용하는 대표적인 이유를 간단히 정리한 학습 문서다.

핵심은 RAG가 LLM에게 회사의 최신·내부 정보를 검색해서 전달하는 구조라는 점이다. 문서를 모델에 다시 학습시키는 대신, 질문이 들어올 때 관련 내용을 찾아 답변의 근거로 사용한다.

## 1. RAG 전체 흐름

RAG는 크게 문서를 미리 준비하는 단계와 사용자의 질문에 답하는 단계로 나뉜다.

```text
[문서 준비 단계]
문서 수집 → 파싱 → Chunking → Embedding → Vector DB 저장

[질문 처리 단계]
사용자 질문 → 질문 Embedding → 관련 Chunk 검색
            → Context 구성 → LLM 호출 → 답변 + 출처
```

문서 준비 단계는 자주 실행되지 않지만, 질문 처리 단계는 사용자가 질문할 때마다 실행된다.

## 2. 핵심 개념

### 2.1 Document Ingestion

외부 문서를 RAG가 처리할 수 있는 형태로 가져오는 과정이다.

```text
Markdown, PDF, GitHub, Notion, DB
                ↓
             문서 수집
```

초기 MVP에서는 여러 소스를 지원할 필요 없이 Markdown 파일이나 GitHub 문서 하나로 시작해도 된다.

### 2.2 Parsing

파일의 형식을 읽고 본문과 필요한 정보를 추출하는 과정이다.

예를 들어 Markdown에서 제목, 본문, 코드 블록을 읽고 PDF에서 텍스트를 추출한다. 파싱이 잘못되면 이후 Chunking과 검색 품질도 함께 나빠진다.

### 2.3 Chunking

긴 문서를 검색하기 적절한 작은 단위로 나누는 과정이다.

```text
긴 문서
  ↓
주문 생성 관련 내용
결제 관련 내용
주문 취소 관련 내용
환불 관련 내용
```

문서 전체를 하나의 검색 단위로 사용하면 질문과 관련된 부분만 정확히 찾기 어렵다. 반대로 너무 작게 나누면 앞뒤 문맥이 사라질 수 있다.

초기에는 Markdown의 제목과 소제목을 기준으로 나누는 방식이 이해하기 쉽다.

### 2.4 Embedding

텍스트의 의미를 비교할 수 있도록 숫자 벡터로 변환하는 과정이다.

```text
"결제 후 주문을 취소하려면?"
              ↓
       [0.12, -0.83, 0.41, ...]
```

문서 Chunk와 사용자 질문을 같은 Embedding 모델로 변환하면 의미가 비슷한 텍스트의 벡터가 가까워진다. 정확히 같은 단어가 없어도 의미를 기준으로 검색할 수 있는 이유다.

Embedding은 번역이나 요약이 아니다. 텍스트를 의미 비교가 가능한 숫자 표현으로 바꾸는 것이다.


> [질문]
> 숫자 벡터란 무엇인가? 좀 쉬운 설명이 가능한가?
> 
> [추가 답변]
> 숫자 벡터는 텍스트의 의미를 여러 개의 숫자로 표현한 목록이다. 숫자 하나가 특정 단어 하나를 뜻하는 것은 아니며, 문장 전체의 의미를 모델이 계산해 만든 좌표에 가깝다.
>
> 예를 들어 다음처럼 표현될 수 있다.
>
> ```text
> "주문을 취소하고 싶어요"
>           ↓
> [0.12, -0.83, 0.41, ...]
> ```
>
> "결제한 주문을 취소하려면?"처럼 의미가 비슷한 문장은 벡터도 가까운 위치에 놓인다. RAG는 이 거리를 계산해 질문과 의미가 가까운 문서 Chunk를 찾는다. 실제 벡터는 보통 수백~수천 개의 숫자로 이루어진다.
> 
> [추가 질문2]
> 여기서 말하는 "모델"이란 무엇인지?
> 
> [추가 답변]
> 여기서 말하는 **모델**은 텍스트를 입력받아 특정 결과를 계산해주는 AI 프로그램이다. 많은 텍스트를 학습하면서 문장과 단어가 어떤 의미 관계를 가지는지 익힌다.
>
> RAG에서는 주로 두 종류의 모델을 사용한다.
>
> 1. **Embedding 모델**
>    - 문서 Chunk나 사용자 질문을 숫자 벡터로 변환한다.
>    - 목적은 답변을 만드는 것이 아니라, 의미가 비슷한 내용을 검색할 수 있게 하는 것이다.
>
> 2. **LLM(대규모 언어 모델)**
>    - 검색된 Chunk와 사용자 질문을 입력받아 사람이 읽을 수 있는 답변을 만든다.
>    - 예: GPT, Claude, Gemini 같은 모델
>
> ```text
> 문서 Chunk ──→ Embedding 모델 ──→ 숫자 벡터 ──→ Vector DB 저장
> 사용자 질문 ─→ Embedding 모델 ──→ 질문 벡터 ──→ 관련 Chunk 검색
>                                                   ↓
>                                      질문 + 검색 결과
>                                                   ↓
>                                                  LLM
>                                                   ↓
>                                                답변
> ```
>
> 따라서 앞에서 말한 "같은 Embedding 모델"이라는 표현은 문서와 질문을 숫자 벡터로 바꿀 때 동일한 변환 기준을 사용해야 한다는 뜻이다. Embedding 모델과 LLM은 서로 다른 역할을 담당할 수 있으며, 하나의 모델이 두 역할을 모두 맡을 필요는 없다.
>
>
### 2.5 Vector DB / Vector Store

Embedding 결과인 벡터와 원본 Chunk, 출처, 문서 ID 같은 정보를 저장하고 유사도 검색을 수행하는 저장소다.

```text
Chunk 원문
Embedding 벡터
문서 ID
출처
제목
```

초기 MVP에서는 PostgreSQL에 pgvector 확장을 붙여 사용할 수 있다. pgvector는 PostgreSQL에서 cosine distance, L2 distance 등의 벡터 검색을 지원한다.

- 질문 : pgvector 란 무엇이며 , cosine distance, L2 distance 는 쉽게 말하면 무엇인가? 나는 전혀 모르는 개념이라 쉬운 설명이 필요

> [추가 답변]
> **pgvector**는 PostgreSQL에 벡터 저장과 유사도 검색 기능을 추가하는 확장 기능이다. PostgreSQL 테이블에 Chunk 원문과 Embedding 벡터를 함께 저장하고, 질문 벡터와 가까운 Chunk를 SQL로 찾을 수 있게 해준다.
>
> **Distance**는 두 벡터가 얼마나 가까운지를 나타내는 값이다. 가까울수록 의미가 비슷하다고 판단한다.
>
> **Cosine distance**는 두 벡터가 가리키는 방향의 차이를 보는 방식이다. 문장의 길이보다 의미의 방향을 비교하는 데 적합해 텍스트 검색에서 자주 사용한다.
>
> **L2 distance**는 두 벡터 사이의 직선거리를 계산하는 방식이다. 숫자 좌표 사이의 실제 거리를 비교한다고 생각하면 된다.
>
> ```text
> 질문 벡터 ── 가까운 거리 ── "결제 취소 방법" Chunk
> 질문 벡터 ───── 먼 거리 ─── "인사 평가 기준" Chunk
> ```
>
> 초기 구현에서는 두 방식의 수학적 차이를 깊이 이해하기보다, 하나의 방식을 정하고 실제 질문 세트에서 검색 결과가 좋은지 비교하면 된다. pgvector의 cosine distance 연산자는 `<=>`, L2 distance 연산자는 `<->`이다.

### 2.6 Retrieval

사용자 질문과 의미가 가까운 Chunk를 Vector DB에서 찾아오는 과정이다.

```text
질문 Embedding
      ↓
Vector DB 유사도 검색
      ↓
관련 Chunk Top-K개
```

여기서 K는 몇 개의 Chunk를 가져올지 나타낸다. 너무 적으면 필요한 내용이 빠질 수 있고, 너무 많으면 LLM에 불필요한 내용이 들어갈 수 있다.

- 질문 : 질문 embedding 은 어떻게 로직이 이루어지는가? 쉽게 예를 들어보면 좋을듯.

> [추가 답변]
> 질문 Embedding은 문서 Chunk를 Embedding하는 과정과 같은 방식으로 이루어진다.
>
> ```text
> 문서 Chunk → Embedding 모델 → 문서 벡터 → Vector DB 저장
> 사용자 질문 → 같은 Embedding 모델 → 질문 벡터
> 질문 벡터 → Vector DB에서 가까운 문서 벡터 검색
> ```
>
> 예를 들어 문서에 "결제 완료 후 주문 취소 요청을 처리한다"가 있고 사용자가 "결제한 주문을 취소하려면?"이라고 질문하면, 두 문장을 각각 벡터로 바꾼 뒤 거리를 계산한다. 단어가 완전히 일치하지 않아도 의미가 가까우면 해당 Chunk가 검색된다.
>
> 중요한 점은 문서와 질문에 **같은 Embedding 모델**을 사용해야 한다는 것이다. 서로 다른 기준으로 만든 벡터는 거리 비교의 의미가 달라질 수 있다.

### 2.7 Context

검색된 Chunk 중 LLM에 전달할 내용을 정리한 것이다.

```text
질문
+ 관련 문서 Chunk
+ 답변 규칙
        ↓
      Prompt
```

검색 결과를 무조건 모두 넣는 것이 아니라 중복을 줄이고, 길이를 조정하고, 출처 정보를 함께 넣는다.

### 2.8 Generation

LLM이 사용자 질문과 검색된 Context를 바탕으로 최종 답변을 생성하는 단계다.

RAG에서 LLM은 문서 검색을 직접 담당하지 않는다. Retriever가 찾아온 내용을 읽고 답변을 만든다.

- 질문 : 그러면 LLM 은 RAG 를 통해 가져온 데이터 말고는 따로 답변 보완을 할 다른 데이터를 생성하거나 검색하지는 않는가? 아니면 RAG 를 통해 가져온 답변 내용을 LLM 은 다듬기만 하는건가?

> [추가 답변]
> 기본적인 RAG에서 LLM은 Retriever가 가져온 Context를 중심으로 답변을 만든다. 단순히 문장을 복사하는 것이 아니라, 여러 Chunk의 내용을 합치고 질문에 맞게 요약·정리·추론할 수 있다.
>
> 동시에 LLM은 학습 과정에서 알고 있던 일반 지식을 바탕으로 문장을 보완할 수도 있다. 따라서 RAG가 가져온 내용만 사용한다고 자동으로 보장되는 것은 아니다.
>
> 이를 통제하려면 Prompt에 다음과 같은 규칙을 둔다.
>
> ```text
> 제공된 Context에 근거해서만 답변한다.
> 근거가 없으면 "문서에서 확인할 수 없습니다"라고 답한다.
> 답변에 사용한 출처를 함께 표시한다.
> ```
>
> 그래도 LLM이 근거 없는 내용을 만들 가능성은 남아 있으므로, 출처 표시와 별도의 평가가 필요하다. 초기 MVP에서는 "검색된 Context에 없는 내용은 추측하지 않는다"는 정책을 적용하고, 근거가 없을 때의 응답도 테스트하는 것이 좋다.
### 2.9 Citation / Provenance

답변의 근거가 된 문서와 위치를 함께 보여주는 기능이다.

```text
답변: 결제 완료 후 주문 취소 요청을 처리한다.
출처: order-cancel.md, 주문 취소 섹션
```

출처를 보여주면 사용자가 답변을 검증할 수 있고, 시스템이 어떤 문서를 근거로 답변했는지 추적할 수 있다.

## 3. 일반적인 RAG 구조

보통 RAG는 문서 색인 흐름과 질문 처리 흐름을 분리한다.

```text
                    ┌──────────────────────┐
                    │      문서 소스       │
                    │ GitHub / Wiki / PDF  │
                    └──────────┬───────────┘
                               │
                               ▼
                    ┌──────────────────────┐
                    │ Ingestion Pipeline   │
                    │ 수집·파싱·Chunking   │
                    │ Embedding·색인       │
                    └──────────┬───────────┘
                               │
                               ▼
                    ┌──────────────────────┐
                    │ Vector Store         │
                    │ Chunk + Vector       │
                    │ + Metadata           │
                    └──────────┬───────────┘
                               │
                               │ 검색
                               ▼
사용자 질문 → API → Query Embedding → Retrieval
                                      │
                                      ▼
                              Context Builder
                                      │
                                      ▼
                                     LLM
                                      │
                                      ▼
                              답변 + 출처 반환
```

### 문서 색인 흐름

```text
문서 수집
  ↓
텍스트 추출
  ↓
Chunking
  ↓
Embedding 생성
  ↓
Chunk, 벡터, 메타데이터 저장
```

### 질문 처리 흐름

```text
질문 수신
  ↓
질문 Embedding 생성
  ↓
Vector Search
  ↓
관련 Chunk 선택
  ↓
Prompt 구성
  ↓
LLM 호출
  ↓
답변과 출처 반환
```

기업 환경에서는 여기에 다음 기능이 추가되는 경우가 많다.

- Keyword Search와 Vector Search를 함께 사용하는 Hybrid Search
- 검색 결과의 순서를 다시 평가하는 Reranking
- 문서 변경 시 변경된 부분만 다시 색인하는 증분 색인
- 사용자의 권한에 맞는 문서만 검색하는 접근 제어
- 검색 품질, 답변 정확성, 지연시간, 비용을 측정하는 평가 시스템

- 질문 : 이 내용들을 쉬운 예시와 함께 다시 설명해주면 이해하기 편할것 같음

> [추가 설명 예시]
> **Hybrid Search**는 두 종류의 검색을 함께 사용하는 방식이다.
>
> ```text
> 질문: ERR_PAYMENT_1032의 원인은?
>              │
>       ┌──────┴──────┐
>       ▼             ▼
>   키워드 검색     의미 검색
>   정확한 코드     비슷한 설명
>       └──────┬──────┘
>              ▼
>       결과를 합쳐 사용
> ```
>
> 키워드 검색은 `ERR_PAYMENT_1032` 같은 오류 코드와 버전 번호를 정확히 찾는 데 강하다. Vector Search는 "결제 승인 실패 원인"처럼 표현이 달라도 의미가 비슷한 내용을 찾는 데 강하다.
>
> **Reranking**은 처음에 20개를 넓게 찾은 뒤, 질문과 가장 관련 있는 순서로 다시 정렬해 상위 3~5개만 선택하는 과정이다. 예를 들어 검색 결과에 결제 문서와 환불 문서가 함께 섞여 있으면, Reranker가 질문에 더 직접적으로 답하는 Chunk를 위로 올린다.
>
> **증분 색인**은 문서가 바뀌었을 때 모든 문서를 다시 처리하지 않고 변경된 문서만 Chunking과 Embedding을 다시 하는 방식이다. 문서의 `updated_at`이나 내용의 hash를 비교해 변경 여부를 판단할 수 있다.
>
> **접근 제어**는 검색 전에 사용자가 볼 수 있는 문서만 남기는 것이다. 검색 후에 문서를 숨기는 것이 아니라, Vector DB 검색 조건에 사용자 권한을 반영해야 한다.
>
> **평가 시스템**은 "잘 되는 것 같다"가 아니라 정해진 질문 세트로 검색 결과와 답변을 비교하는 기능이다. 예를 들어 `주문 취소 이벤트는?`이라는 질문에 `payment-cancel.md`가 검색되는지 확인한다.

하지만 초기 MVP에서는 단일 문서 소스, 단순 Chunking, Vector Search, 출처 반환만으로 전체 흐름을 먼저 검증하는 것이 적절하다.

## 4. 기업은 RAG를 무엇을 위해 구축하는가

RAG가 특히 유용한 상황은 다음과 같다.

- 조직 내부 문서를 LLM이 알아야 할 때
- 정보가 자주 바뀌어 모델을 다시 학습시키기 어려울 때
- 답변의 근거와 출처를 확인해야 할 때
- 직원이 여러 시스템을 직접 검색하는 시간이 클 때
- 고객·지원 담당자에게 일관된 답변을 제공해야 할 때

### 4.1 사내 지식 검색

직원들이 Notion, Confluence, Google Drive, Slack, GitHub 등에 흩어진 정보를 한 번에 질문하는 용도다.

예시:

```text
"외부 업체 계약 승인 절차가 어떻게 되나요?"
```

RAG는 사내 규정, 위키, 관련 대화 내용을 검색하고 답변과 원문 링크를 제공할 수 있다.

### 4.2 고객 지원

상품 문서, FAQ, 환불 정책, 과거 티켓을 검색해 상담원의 답변 작성을 돕거나 고객용 챗봇을 제공한다.

주요 효과는 다음과 같다.

- 반복 질문에 대한 응답 시간 단축
- 상담원마다 달라지는 답변의 편차 감소
- 사람이 검토할 수 있는 답변 초안과 출처 제공

고객 지원에서는 실시간 주문·결제·계정 정보가 필요한 경우가 많다. 이런 정보는 문서 검색만으로 해결되지 않으므로, RAG가 백엔드 API나 업무 시스템을 함께 조회하는 구조로 확장될 수 있다.


- 제안 : 우리가 해보려는 이 시스템을 약간 챗봇으로 만들수있는 활용점을 찾아봐도 좋겠다

> [추가 제안]
> 이 프로젝트는 **백엔드 개발자를 위한 사내 기술 문서 챗봇**으로 구체화하는 것이 가장 자연스럽다.
>
> ```text
> Spring Boot, DB, MQ, 장애 대응 문서
>                 ↓
>          기술 문서 RAG 챗봇
>                 ↓
> "주문 취소 이벤트는 어떤 조건에서 발행되나요?"
>                 ↓
>          답변 + 문서 출처
> ```
>
> 이 방향의 장점은 문서의 범위가 비교적 명확하고, 태환님이 기존에 경험한 백엔드 기술과 연결하기 쉽다는 점이다. 고객 지원 챗봇처럼 실시간 주문·결제 API나 개인정보를 처음부터 연동하지 않아도 된다.
>
> 초기 사용자는 백엔드 개발자로 한정하고, 문서도 다음처럼 제한한다.
>
> - API 명세와 사용 예시
> - 주문·결제 처리 흐름
> - 장애 대응 문서와 오류 코드
> - MQ 메시지 처리 규칙
> - 데이터베이스 설계 문서
>
> 질문 예시는 다음과 같다.
>
> - `주문 취소 시 어떤 이벤트가 발행되나요?`
> - `ERR_PAYMENT_1032가 발생하면 어떤 항목을 확인해야 하나요?`
> - `결제 성공 여부는 어떤 기준으로 판단하나요?`
>
> 이 챗봇은 코드를 직접 변경하거나 운영 작업을 실행하지 않고, **문서를 검색해 답변과 출처를 제공하는 읽기 전용 도우미**로 시작하는 것이 안전하다. 이후 검색 품질이 검증되면 GitHub 문서, 장애 티켓, 실시간 운영 데이터 조회 등을 단계적으로 추가할 수 있다.
### 4.3 개발자·기술 지원

API 명세, 운영 매뉴얼, 장애 대응 문서, 코드 저장소, 과거 장애 티켓을 검색해 오류 원인과 해결 방법을 찾는 용도다.

예시:

```text
"ERR_PAYMENT_1032 오류가 발생했을 때 확인할 항목은?"
```

이 사례에서는 의미 검색뿐 아니라 오류 코드처럼 정확한 문자열 검색도 중요하므로, 나중에는 BM25와 Vector Search를 결합한 Hybrid Search가 적합할 수 있다.

### 4.4 신입사원 온보딩

사내 업무 규칙, 시스템 사용법, 팀별 업무 문서를 기반으로 질문에 답하는 온보딩 도우미다.

문서를 직접 찾아 읽는 시간을 줄이고, 담당자가 반복적으로 설명하는 부담을 줄일 수 있다.

### 4.5 영업·회의 준비

CRM, 과거 미팅 기록, 지원 티켓, 제품 사용 현황, 경쟁사 자료 등을 검색해 고객별 사전 브리핑을 만드는 용도다.

### 4.6 법무·컴플라이언스·규정 확인

계약서, 사내 정책, 법령, 규정, 감사 자료에서 관련 조항을 찾아 요약하고 출처를 제시하는 용도다.

이 영역은 잘못된 답변의 위험이 크므로 자동 실행보다 출처 표시와 사람의 최종 검토가 중요하다.

### 4.7 제안서·RFP·보안 질문서 작성

과거 제안서, 제품 설명, 보안 정책, 인증 자료를 검색해 반복적인 답변 초안을 작성하는 용도다.

## 5. 사례에서 공통으로 보이는 구조

회사마다 제품과 데이터 소스는 다르지만, 일반적으로 다음 구조가 반복된다.

```text
[데이터 계층]
사내 문서 / 코드 / 티켓 / CRM / 업무 DB / 외부 API
                 ↓
[수집·색인 계층]
Connector → Parser → Chunker → Embedding → Index
                 ↓
[검색 계층]
Query 분석 → 권한 필터 → Vector Search
                         + Keyword Search
                         → Reranker
                 ↓
[응답 계층]
Context Builder → LLM → 답변·출처·로그
```

프로덕션 환경에서는 추가로 다음을 관리한다.

- 문서의 최신 버전과 변경 시각
- 문서별 접근 권한
- 원문 출처와 답변의 근거
- Embedding 모델 버전
- 검색 결과와 답변 품질
- LLM 호출 비용과 지연시간
- 문서 삭제·변경 시 색인 동기화

## 6. 이 프로젝트의 1단계 범위

이 문서의 개념을 직접 확인하기 위한 최소 구현은 다음과 같다.

```text
Markdown 문서 3~5개
  ↓
제목 기준 Chunking
  ↓
Embedding API 호출
  ↓
PostgreSQL + pgvector 저장
  ↓
질문 Embedding
  ↓
Top-K Vector Search
  ↓
검색 결과를 Prompt에 포함
  ↓
LLM 답변
  ↓
답변 + 문서명·섹션 출처 반환
```

처음부터 넣지 않아도 되는 기능:

- 여러 문서 저장소 연동
- Kafka 또는 MQ
- Redis 캐시
- Elasticsearch Hybrid Search
- Reranker
- Streaming
- 복잡한 ACL
- Scheduler와 대규모 Worker

먼저 확인할 것은 다음 세 가지다.

1. 질문과 관련된 Chunk를 실제로 찾는가
2. LLM이 검색된 문서에 근거해 답변하는가
3. 어떤 문서를 근거로 사용했는지 보여줄 수 있는가
