## 1. 한 줄 요약

**검색은 신뢰할 만한 수준(Hit@1 89%, p95 400ms, 15분 지속 부하에도 에러 0%)이고, 시스템의 실질적 병목은 검색이 아니라 공유 GPU 위 LLM 답변 생성이다** — 동시 요청 10건만 몰려도 평균 답변 latency가 5초→31초로 튀고 타임아웃 실패가 발생한다.

## 2. 실험 환경

- 대상: DGX Spark에 배포된 `my-rag-app`(8090) + `rag-postgres`(5433), Embedding(8003)·LLM(8002)은 Spark의 공유 GPU 자원(BGE-M3 / OpenAI-compatible, GPU: NVIDIA GB10, 서빙 엔진: SGLang)
- 격리 여부: 별도 스테이징 환경을 만들지 않고 배포된 인스턴스에 직접 테스트 — 아직 실사용 트래픽이 없어 안전하다고 판단(`perf/README.md` 참고)
- 실행 위치 정책: 정확도(검색·답변) 평가는 **로컬 Mac**에서도 충분(어차피 같은 Spark Embedding/LLM을 호출하므로 네트워크 왕복 차이가 결과 정확도에 영향 없음). **색인 처리량·k6 부하 테스트는 Spark 네이티브**에서 실행(누적 왕복 횟수·동시성이 핵심이라 Tailscale 경유 시 수치가 왜곡됨)
- 테스트 데이터는 전부 `source` 경로가 `perf-test/{size}/...`로 시작해 운영 데이터와 분리·일괄 삭제 가능

## 3. 데이터셋

`perf/dataset/generate_dataset.py`로 자동 생성한 한국어 합성 문서 6개 도메인(주문취소/환불/배송/회원/결제/장애대응). 정답은 생성 시점에 파라미터로 직접 박아 넣어(LLM 자기 채점 없음) 신뢰할 수 있게 했다.

| 사이즈 | 문서 수 | 청크 수 | 질의 수 | 용도 |
|---|---:|---:|---:|---|
| S | 100 | 400 | 20 | 파이프라인 검증용 |
| M | 1,000 | 4,000 | 150 | 공식 baseline |

질의 카테고리 7종(계획서 §3 기준): `direct_lookup`(기본 검색), `hard_negative`(비슷한 함정 문서 구분), `paraphrase`(표현 변형 강건성), `keyword_identifier`(코드/식별자 정답), `multi_chunk`(여러 청크 종합), `unanswerable`(근거 없음 인지), `ambiguous`(질문 자체가 모호함).

개발 중 데이터셋 생성기 버그를 3건 발견·수정했다(회사명 랜덤 중복 → 가짜 실패, 도메인 간 회사명 충돌, order-cancel 문장에 회사명 누락 → 상세는 커밋 이력 참고). **주의**: M의 150개 질의는 아직 100% 자동 생성이며, `perf/dataset/labeling-guide.md`가 요구하는 사람 검토(최소 20%)는 수행하지 않았다 — 아래 수치는 파이프라인이 낸 신뢰할 만한 결과지만, 사람이 최종 확인한 "포트폴리오 확정치"는 아니다.

로컬 Mac 실행(위 정책상 문제없음), M 150개 질의, `perf/evaluation/evaluate_answers.py`의 1차 규칙 기반 채점(사람 검토용 `answer-rubric.md`는 미작성 — 아래 수치는 근사치):

| 지표 | 값 |

**abstention 정확도가 카테고리별로 극단적으로 갈린다** — 가장 중요한 발견:

|---|---:|
| unanswerable (근거 자체가 없음) | 100% (15/15) |

| category | fact_coverage | source_precision |
|---|---:|---:|

## 6. 색인 처리량

Spark 네이티브, 1회 실행(계획서 권장 3회+warm-up 대신 1회로 축소 — 두 사이즈 처리량이 서로 근접해 재실행 필요성이 낮다고 판단):

| size | 총 소요시간 | 문서/청크 | docs/min | chunks/sec |
|---|---:|---:|---:|---:|
| S | 97.2초 | 100 / 400 | 61.7 | 4.11 |
| M | 949.8초 (15.8분) | 1,000 / 4,000 | 63.2 | 4.21 |

- **처리량이 규모에 거의 영향받지 않는다** (S/M 차이 2.4%, 노이즈 수준) — 최소 1,000 문서까지는 색인 파이프라인에 병목이 누적되지 않는다. L(10,000)/XL(50,000)은 시간 비용 문제로 이번 평가에서 제외했다(§11).
- **Spark 네이티브가 로컬(Mac, Tailscale 경유)보다 39% 빠르다** (61.7 vs 44.5 docs/min) — 색인은 문서마다 Embedding 호출이 누적되는 구조라, 검색/답변 단일 호출과 달리 네트워크 위치가 실질적 차이를 만든다.

## 7. 검색 latency/throughput (k6, Spark 네이티브)

부하 단계 Smoke(1)→Warm(5)→Load(10)→Stress(25)→Soak(8명, 15분). **Saturation(50+)은 공유 GPU/DB 풀 한계로 장애 재현 위험이 있어 1차에서 제외**(별도 승인 필요, §11).

Soak(8 VUs, 15분) 결과 — 가장 상세히 확보된 수치:

| 지표 | 값 |
|---|---:|
| 총 요청 수 | 13,855 |
| 에러율 | 0.00% |
| latency avg / p95 | 318.8ms / 400.3ms |
| RPS | ~15.4 |

15분 내내 latency가 안정적으로 유지됐고 에러가 전혀 없었다 — **메모리 누수나 connection leak 징후 없음**. Smoke/Warm/Load/Stress 단계도 스크립트 실행 로그상 모두 정상 완료(에러율 threshold 20% 미만)했으나, 각 단계의 상세 latency 수치는 이번에 따로 기록하지 못했다(Spark의 `perf/results/search/summary_*.json`에 원본 존재, §11 참고).

## 8. 답변 latency/throughput (k6, Spark 네이티브)

Smoke(1)→Warm(3)→**Load(10)까지만** 진행(계획서 권장 Stress/Saturation은 제외 — LLM이 공유 GPU를 쓰고 무거워 그 이상은 다른 서비스에 실질적 피해를 줄 수 있다고 판단).

Load(10 VUs) 결과:

| 지표 | 값 |
|---|---:|
| 성공률 | 81.8% (18/22) |
| 에러율 | 18.2% |
| latency avg / p95 / max | 31.1s / 52.3s / 60.0s(서버 read-timeout에 걸림) |

Smoke(1명) 기준 요청당 4~5초였던 것과 비교하면, **동시 10명만 돼도 평균 latency가 6배 이상(31초) 치솟는다.** 최대값이 정확히 `llm.read-timeout=60s` 설정값에 걸려있어, 순수 GPU 대기열 지연이 서버 타임아웃으로 이어진 것으로 보인다.

이 테스트 도중 `nvidia-smi` 스냅샷:

```
GPU-Util: 96%
Processes: sglang::scheduler  83421MiB (LLM 서빙 엔진)
```

GPU가 이미 96% 활용 중이었다 — 이는 뒤이은 §9의 근본 원인 분석과 직결된다.

## 9. 병목 분석

### 9.1 검색은 병목이 아니다
Stress(25명)까지 진행하는 동안 검색 쪽에서 눈에 띄는 문제가 없었다. 현재 규모(4,000 청크)의 exact-scan 방식으로도 충분히 여유가 있다 — HNSW/IVFFlat 같은 벡터 인덱스 도입(계획서 Task 7)은 **지금은 근거가 없어 진행하지 않았다.**

### 9.2 `paraphrase` 카테고리 약점 — 근본 원인은 데이터, 진짜 한계는 임베딩
결제 도메인 문서 중 여러 개가 `retry_count`(2/3/5 세 값뿐) 같은 사실을 공유하면서 회사명(고유번호)만 다르다. 순수 코사인 유사도가 보일러플레이트 문장 속 고유명사만으로 문서를 구분하기 어려워한다 — `hard_negative`가 93%+로 정상 작동하는 걸 보면 검색 자체는 건강하고, 이건 "많은 근접 중복 문서를 고유명사로만 구분해야 하는" 특정 케이스의 한계다. **하이브리드 검색(BM25+벡터) 또는 재순위화(reranking)** 도입 시 개선 여지가 있다.

### 9.3 `ambiguous` 질문에서 전혀 거절하지 않음 — 실제 기능 결함
`AnswerService`/`SearchService`에 유사도 임계값이 없다(top-K가 관련성과 무관하게 항상 채워짐). 그 결과 "근거가 아예 없음"(unanswerable, 100% 거절)과 "근거가 여러 개라 헷갈림"(ambiguous, 0% 거절)을 시스템이 구분하지 못한다. **결과 상위권 거리(distance) 값들의 마진(margin)이 좁을 때를 별도로 감지**하는 로직 추가가 필요하다 — 측정을 먼저 하고 결정하자는 원칙에 따라 이번엔 고치지 않고 현상만 기록했다.

### 9.4 `multi_chunk` 답변 합성 누락 — 검색이 아니라 LLM 단계 문제
검색은 관련 청크 100% 다 찾아오는데 답변에는 70%만 반영된다. Context는 다 전달됐다는 전제 하에(코드 상 `contextBuilder.build()`가 검색 결과를 그대로 넣음), LLM이 여러 근거를 종합하는 데 실패하는 경우가 있다 — prompt에 "여러 출처의 사실을 빠짐없이 정리하라"는 지시를 강화하거나, few-shot 예시 추가로 개선 여지가 있다.

### 9.5 (핵심) LLM 답변 생성 동시성 병목과 해결 방안

**원인**: `sglang::scheduler`가 GPU를 96% 점유한 상태에서 동시 요청이 큐에 쌓여 순차적으로(혹은 제한된 배치로) 처리된다. 이는 애플리케이션 코드의 버그가 아니라 **공유 GPU 서빙 계층의 용량 한계**다.

**해결 방안 (비용/효과 순, 실제 구현은 이번 범위 밖 — 로드맵으로 남김):**

1. **(즉시 가능, 코드 최소) 앱 레벨 동시성 제한 + 빠른 거절**: 지금은 들어오는 모든 답변 요청을 제한 없이 LLM에 그대로 넘겨서, 몰리면 "모두가 다같이 느려지는" 구조다. `AnswerService`에 세마포어(예: 동시 3~5개)를 걸어 초과분은 즉시 503/429로 거절하면, 일부 사용자는 빠르게 "다시 시도하라"는 응답을 받고 나머지는 정상 속도를 유지한다 — 전체가 30초씩 걸리는 것보다 나은 사용자 경험이다. 코드 변경량이 가장 적고 즉시 효과가 있다.
2. **(즉시 가능, 설정값 변경) `max_tokens`/context 크기 축소**: 현재 `LLM_MAX_TOKENS=512`, `LLM_MAX_CONTEXT_CHARS=12000`. 실제 답변 길이 분포를 보고 필요 이상으로 크면 줄이는 것만으로 요청당 GPU 연산량(특히 생성 단계)이 줄어 전체 처리량이 늘어난다.
3. **(UX 개선, 처리량은 그대로) 스트리밍 응답**: 답변을 토큰 단위로 스트리밍하면 총 소요 시간은 그대로여도 사용자가 체감하는 "첫 응답까지의 시간"은 크게 줄어든다. 근본적 처리량 문제 해결은 아니지만 체감 개선 효과가 크다.
4. **(사용 패턴에 따라) 답변 캐싱**: 동일하거나 매우 유사한 질문이 반복되는 사용 패턴이라면, 질문(또는 검색된 청크 조합) 기준 캐싱으로 LLM 호출 자체를 줄일 수 있다. 지금은 실사용 트래픽이 없어 반복 질문 비율을 알 수 없으므로 추측성 최적화 — 실사용 데이터가 쌓인 뒤 재검토.
5. **(인프라 레벨) 전용 GPU 용량 확보 또는 서빙 스케일아웃**: 근본적으로는 지금 이 LLM 서버를 다른 ~20개 프로젝트와 공유하는 게 한계의 원인이다. 이 프로젝트만을 위한 전용 GPU/모델 복제본을 두거나, SGLang 자체의 배치 설정(`--max-running-requests` 등)을 이 정도 동시성에 맞게 튜닝하는 게 정공법이지만, 개인 Spark 환경에서는 비용/자원 제약이 커서 지금 단계에서는 우선순위가 낮다.

**권장 순서**: 지금 MVP 단계에서 실사용 트래픽이 없다는 걸 감안하면, 당장은 1번(동시성 제한)만 넣어도 "몰릴 때 전체가 느려지는" 최악의 상황은 막을 수 있다. 2번은 설정값 튜닝이라 비용이 거의 없어 같이 적용해볼 만하다. 3~5번은 실사용 데이터가 쌓이거나 실제 SLA 요구가 생긴 뒤 재검토하면 된다.

## 10. 최적화 전후 비교

수행하지 않음 — Task 7(HNSW/IVFFlat 비교)은 §9.1의 이유로 이번 평가에서 근거가 부족해 스킵했다. §9.5의 LLM 동시성 개선안도 아직 구현 전이라 전후 비교 대상이 없다.

## 11. 실패·미검증 항목

- **L/XL(10,000/50,000 문서) 색인·검색 성능**: 로컬/Spark 소요 시간 추정상 너무 오래 걸려 이번 평가에서 제외. 지금까지의 선형적 처리량 패턴이 이 규모에서도 유지되는지는 미검증.
- **검색 부하 Smoke/Warm/Load/Stress의 상세 latency 수치**: 스크립트 로그상 모두 threshold(에러율 20%) 통과로 정상 완료했으나, 이번 보고서에는 Soak 단계 수치만 상세히 반영했다. 원본은 Spark의 `~/services/my-rag/perf/results/search/summary_{smoke,warm,load,stress}.json`에 있다.
- **답변 부하 Smoke/Warm 상세 수치**: 마찬가지로 Load 단계만 상세 반영. 최초 실행 시 `run_answer_load.sh`의 `set -e`가 k6의 threshold 실패 종료 코드와 상충해 Smoke 이후 단계가 실행되지 않는 스크립트 버그가 있었고(수정 완료, 재실행으로 Load까지 확보), 수정 전 원래의 Smoke 결과(표본 2개, 의미 없는 수치)는 폐기했다.
- **Saturation(검색 50명+) 단계**: 공유 GPU/DB 풀 한계로 장애 재현 위험이 있어 의도적으로 제외. 별도 승인 후 재검토 가능.
- **사람 검토 gold set**: M의 150개 질의는 `labeling-guide.md`가 요구하는 사람 검토(최소 20%)를 거치지 않은 100% 자동 생성 데이터다.
- **답변 품질 2차 평가(사람 rubric)**: `answer-rubric.md` 미작성, `evaluate_answers.py`의 1차 규칙 기반 채점만 수행했다.
- **DB 커넥션 풀(기본 10) 한계**: Stress(25 VUs, 검색)가 이 풀 크기를 초과했음에도 명시적 에러 급증이 이번에 상세 기록되지 않아, 실제로 병목으로 작용했는지 별도 확인이 필요하다.

## 12. 재현 방법

```text
1. perf/dataset/generate_dataset.py --size m --out-dir <dir> --queries-out queries_m.jsonl --query-sample-size 150
2. 생성된 perf-test/m/ 문서를 Spark data/markdown/perf-test/m/에 업로드
3. POST /api/documents/index 로 색인
4. perf/dataset/resolve_chunk_keys.py 로 chunk key 채우기
5. perf/evaluation/evaluate_retrieval.py, evaluate_answers.py 로 정확도 측정
6. perf/load/index_benchmark.py (또는 run_index_benchmark.sh) 로 색인 처리량 측정
7. perf/load/run_search_load.sh, run_answer_load.sh 로 k6 부하 측정(Spark에서 직접 실행)
```

시드 고정(`--seed` 기본 42)이라 같은 조건이면 동일한 데이터셋이 재생성된다.

## 13. 포트폴리오용 핵심 수치

- 검색 정확도: **Hit@1 89.2%, MRR 0.899** (M, 1,000 문서/150 질의)
- 검색 latency: **p50 227.8ms / p95 291.9ms**(단일 요청), 15분 지속 부하(8명 동시)에서도 **에러 0%, p95 400ms**
- 답변 정확도: **fact_coverage 87.1%, source_precision 90.8%**
- 색인 처리량: **분당 ~62 문서** (Spark 네이티브, 규모 무관하게 안정적)
- **핵심 병목**: 동시 답변 요청 10건에서 평균 latency 5초→31초 (공유 GPU LLM 서빙 한계, §9.5에 해결 방안 정리)
