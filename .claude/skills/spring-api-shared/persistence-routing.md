# 데이터 접근 방식 선택

JPA와 MyBatis를 의존성 이름만으로 선택하지 않는다. 대상 도메인의 실제 호출 흐름과 기존 구현을 우선한다.

## 분기 순서

1. 대상 Controller가 호출하는 Service의 데이터 접근 경로
2. 같은 도메인의 Repository·Mapper 구조
3. 기존 테스트와 프로젝트 지침
4. 빌드 의존성

완료 기준: 이번 API가 따를 데이터 접근 방식과 근거 파일을 제시할 수 있다.

## JPA 사용 근거

- `JpaRepository`, `CrudRepository` 계열
- `@Entity`, `@Repository`
- Entity 연관관계와 Repository 쿼리 메서드
- 기존 Repository 또는 통합 테스트

JPA를 선택하면 기존 Entity 구성, 트랜잭션 범위, 조회 방식과 쿼리 작성 관례를 따른다. 편의를 위해 새 연관관계나 cascade 설정을 추가하지 않는다.

## MyBatis 사용 근거

- `@Mapper`
- Mapper XML
- SQL 애너테이션
- 기존 Mapper·SQL 테스트

MyBatis를 선택하면 애너테이션/XML 중 대상 도메인의 기존 방식을 따른다. 결과 매핑, 파라미터 이름과 동적 SQL 작성 방식을 확인한 뒤 구현한다.

## 두 기술이 함께 있을 때

프로젝트 전체 의존성보다 대상 도메인의 기존 방식을 따른다. 한 API 안에 새 JPA와 MyBatis 경로를 동시에 도입하지 않는다. 공통 전환이 필요하면 API 작업과 분리해 사용자 승인을 받는다.

## DB 접근이 없거나 방식을 판단하기 어려울 때

- 데이터 접근이 필요 없는 API면 불필요한 Repository·Mapper를 만들지 않는다.
- JPA/MyBatis 어느 쪽도 근거가 없으면 임의 도입하지 않는다.
- JDBC, 외부 API, 캐시가 실제 데이터 원본이면 기존 구조를 확인하고 1차 지원 범위와의 차이를 보고한다.

## DB 변경 범위

API 작업이 DB 스키마·데이터 변경을 필요로 하면 다음을 분리해 제시한다.

- API 코드 변경
- 마이그레이션 또는 DDL
- 기존 데이터 처리
- 문제 발생 시 원복 방법과 기존 기능에 미치는 영향

테이블·컬럼·데이터 삭제는 API 삭제에 포함된 것으로 간주하지 않는다. 명시적 사용자 승인 없이 수행하지 않는다.
