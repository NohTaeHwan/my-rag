# 테스트 우선 개발 절차(TDD)

모든 API 추가·수정·삭제는 실패하는 테스트 작성(RED), 최소 구현으로 테스트 통과(GREEN), 동작을 유지하며 코드 정리(REFACTOR) 순서로 진행한다. Hook은 이 과정을 대신하지 않는다.

## 1. 구현할 동작 정리

구현 전에 다음을 명확히 한다.

- HTTP 메서드와 경로
- 인증·인가 경계
- 요청 파라미터·본문과 검증
- 정상 응답과 실패 상태
- 데이터 없음, 중복, 경계값
- 기존 호출자에 미치는 영향

구현 방식에 영향을 주는 불명확한 항목만 사용자에게 질문한다.

완료 기준: 정상·실패 동작을 테스트 이름과 검증문으로 표현할 수 있다.

## 2. 실패하는 테스트 작성(RED)

가장 작은 동작 하나의 테스트를 먼저 작성하고 대상 모듈의 실제 명령으로 실행한다.

- Controller: 경로, 입력, 상태, 응답, Service 전달값
- Service: 비즈니스 규칙, 데이터 없음, 충돌, 경계값
- 데이터 접근: 프로젝트가 기존에 사용하는 테스트 수준

확인 사항:

- 실패가 테스트 문법이나 설정 오류가 아니다.
- 실패 이유가 구현되지 않은 새 동작 또는 아직 남아 있는 기존 동작이다.
- 테스트가 기존 구현 없이 바로 통과하면 assertion과 경로를 다시 확인한다.

완료 기준: 실행 명령, 실패 테스트, 예상한 실패 이유를 기록했다.

## 3. 최소 구현으로 테스트 통과(GREEN)

실패 테스트를 통과시키는 최소 코드만 작성한다. 기존 계층과 예외·응답 패턴을 유지한다.

여러 동작의 테스트와 구현을 한꺼번에 작성하지 않는다. 정상 동작 하나를 Controller에서 데이터 접근까지 완성한 뒤 실패·경계 동작을 하나씩 같은 순서로 진행한다.

완료 기준: 방금 실패했던 테스트가 같은 명령에서 통과한다.

## 4. 동작을 유지하며 코드 정리(REFACTOR)

관련 테스트가 통과한 뒤에만 중복 제거, 이름 개선과 작은 메서드 추출을 수행한다. 새 동작을 추가하지 않으며, 코드 정리 후 영향받는 테스트를 다시 실행한다.

완료 기준: 관련 테스트가 계속 통과하고 요청 밖 리팩터링이 없다.

## 5. 작업 유형별 실패 테스트 작성 기준

### 추가

새 API 경로의 정상 동작 테스트부터 작성하고, 입력 검증·예외·인증·경계값 테스트를 차례로 추가한다.

### 수정

유지할 기존 동작의 테스트가 통과하는지 먼저 확인한다. 테스트가 부족하면 현재 동작을 확인할 수 있는 테스트를 추가한 뒤, 바꿀 동작이 현재 코드에서 실패하도록 테스트를 작성한다.

### 삭제

삭제 후 API 경로가 존재하지 않아 반환되는 표준 404 또는 승인된 폐기 응답을 테스트한다. 기존 API 경로가 남아 있어 테스트가 실패하는지 확인한 후 제거한다. 다른 API가 공유하는 코드의 테스트도 계속 통과해야 한다.

## 6. 테스트를 다시 실행하는 기준

- 실패 테스트와 구현 후 통과 테스트는 Claude가 직접 실행한다.
- 마지막 테스트 통과 이후 코드가 바뀌면 영향받는 테스트를 다시 실행한다.
- 코드가 바뀌지 않았다면 보고서 작성을 위해 동일 테스트를 반복하지 않는다.
- Stop Hook의 재실행은 마지막 코드 변경 이후 독립 검증이므로 허용된 중복이다.
- Hook이 찾는 대응 테스트가 전체 관련 테스트라고 가정하지 않는다.
