# 프로젝트 구조 확인

API 코드를 수정하기 전에 프로젝트의 실제 구조와 규칙을 확인한다. 추측하지 말고 프로젝트 파일과 기존 구현을 근거로 판단한다.

## 1. 적용 지침과 Git 상태

1. 현재 작업 디렉터리에 적용되는 `CLAUDE.md`와 저장소 지침을 읽는다.
2. 프로젝트 루트 지침에서 이번 작업과 관련된 문서를 확인한다.
3. Git 상태를 확인해 기존 사용자 변경과 이번 작업 범위를 구분한다.
4. 신규 추가, 기존 수정, 제거·폐기 중 작업 유형을 확정한다.

관련 문서 안내가 없으면 README, 빌드 파일, 기존 코드·테스트·명세 파일을 확인한다. 특정 이름의 문서가 없다는 이유로 새 문서를 임의 생성하지 않는다.

완료 기준: 적용할 규칙, 읽은 문서, 기존 변경, 이번 작업 범위를 설명할 수 있다.

## 2. 지원 범위 확인

1차 지원 범위:

- Java 기반 Spring Boot
- Spring MVC REST API
- Gradle 또는 Maven
- JPA 또는 MyBatis
- 프로젝트에 존재할 때만 OpenAPI

다음이 주 구현 경로면 범위 밖임을 알리고 MVC 절차를 강제하지 않는다.

- Kotlin
- WebFlux
- GraphQL
- R2DBC

Java와 Spring Boot 버전은 고정하지 않는다. 실제 build 설정과 기존 테스트 패턴을 따른다.

완료 기준: 지원 범위 안의 Java Spring MVC 작업인지 확인했다.

## 3. 빌드 도구 확인

다음 순서로 결정한다.

1. 대상 모듈 또는 상위 저장소 루트에 `gradlew`가 있으면 해당 Wrapper와 모듈 지정 문법을 우선한다.
2. 대상 모듈 또는 상위 저장소 루트에 `mvnw`가 있으면 해당 Wrapper와 모듈 지정 문법을 우선한다.
3. `build.gradle` 또는 `build.gradle.kts`만 있으면 README·CI의 Gradle 명령
4. `pom.xml`만 있으면 README·CI의 Maven 명령
5. 둘 이상이면 대상 Controller의 모듈과 기존 CI 명령으로 선택
6. 여전히 불명확하면 사용자에게 확인

Wrapper가 있으면 시스템 `gradle`·`mvn`보다 우선한다. Wrapper를 임의 생성하지 않는다.

완료 기준: 대상 모듈, 빌드 도구, 실제 실행할 테스트·컴파일 명령의 근거가 있다.

## 4. 기존 호출 흐름 추적

다음 순서로 관련 구현을 읽는다.

```text
HTTP 요청 경로
→ 요청·응답 모델
→ Controller
→ Service
→ 데이터 접근
→ 예외·공통 응답
→ Controller·Service·통합 테스트
```

같은 도메인의 기존 패턴과 비슷한 다른 도메인의 구현을 함께 비교한다. 새 타입·유틸·추상화를 만들기 전에 재사용 가능한 구조를 확인한다.

완료 기준:

- 요청부터 데이터 접근까지 흐름을 설명할 수 있다.
- 수정 대상과 영향을 받는 호출부를 확인했다.
- 기존 테스트 방식과 명명 규칙을 확인했다.
