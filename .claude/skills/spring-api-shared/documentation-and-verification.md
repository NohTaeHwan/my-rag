# API 명세·문서 업데이트와 최종 확인

프로젝트에서 관리 중인 API 명세와 관련 문서에만 변경 내용을 반영한다. 기존에 없는 문서 관리 방식을 새로 만들지 않는다.

## 1. OpenAPI와 API 명세 확인

다음 항목이 하나 이상 있으면 프로젝트에서 OpenAPI를 관리하는 것으로 판단한다.

- springdoc 또는 Swagger 관련 의존성
- OpenAPI YAML·JSON
- 기존 `@Operation`, `@Schema` 등 애너테이션
- 프로젝트 루트 지침에 적힌 OpenAPI 관련 문서

OpenAPI를 관리하고 있다면 기존 작성 방식을 따른다.

- 애너테이션 기반: 실제 Controller·요청·응답 변경을 애너테이션에도 반영
- OpenAPI 파일을 먼저 작성하는 방식(spec-first): OpenAPI 파일을 업데이트하고 프로젝트의 검증 명령 실행
- 별도 interface 방식: 프로젝트에서 이미 사용하고 있을 때만 유지

OpenAPI가 없으면 관련 의존성, 애너테이션과 파일을 추가하지 않는다. Spring REST Docs 등 다른 명세 체계가 있으면 그 방식을 따른다.

완료 기준: 사용 중인 명세 체계와 변경 파일을 근거로 제시하거나 적용 대상 없음으로 확인했다.

## 2. 프로젝트 문서

프로젝트 루트 지침에서 이번 작업과 관련된 문서를 확인하고 변경 내용을 반영한다.

- API 구현 현황
- 요청·응답 구조
- DB 스키마와 마이그레이션
- 인증·인가
- 설계 결정

문서를 찾지 못했다는 이유로 특정 이름의 문서를 만들지 않는다. README 날짜나 버전은 실제 내용 변경과 프로젝트 규칙이 있을 때만 수정한다.

임시 검증용 API에도 프로젝트의 API 명세·문서 작성 규칙을 동일하게 적용한다. 프로젝트 루트 지침이 API마다 명세·구현 현황·README 업데이트를 요구하면 그대로 수행한다. 생략해야 한다면 먼저 사용자 승인을 받는다.

완료 기준: 코드와 실제 프로젝트 문서 사이에 알려진 불일치가 없고, 필수 문서를 생략했다면 사용자 승인 근거가 있다.

## 3. Claude와 Hook이 확인할 범위

Claude가 직접 확인한다.

- 구현 전에 작성한 테스트가 실패한 이유(RED)
- 필요한 코드를 구현한 뒤 관련 테스트가 통과한 결과(GREEN)
- 요청·응답 변경이 기존 호출부에 미치는 영향
- 프로젝트에서 관리 중인 API 명세와 관련 문서의 업데이트 여부
- Hook이 찾지 못하는 관련 테스트

Stop Hook이 독립적으로 수행한다.

- 코드 변경 마커 기반 컴파일
- 같은 위치의 대응 테스트
- diff에서 찾은 위험 신호와 검수 내용(feedback)

Hook이 통과했다는 이유만으로 모든 관련 테스트를 실행했거나 요구한 동작이 정확하다고 판단하지 않는다.

## 4. 최종 확인

마지막 코드 변경 이후 다음을 확인한다.

1. 영향받는 관련 테스트의 실제 결과
2. 대상 모듈 컴파일 또는 프로젝트가 정한 검증 명령
3. `git diff --check`
4. 최종 diff와 기존 사용자 변경 구분
5. 명세·문서 변경 여부
6. 실행하지 못한 검증과 남은 위험

Stop Hook이 마지막 변경 이후 실행될 예정이면 동일 명령을 보고용으로 반복하지 않는다. Hook 이후 코드를 다시 바꾸면 영향받는 검증을 재실행한다.

## 5. 최종 보고 형식

- 구현하거나 제거한 API 동작
- 기존 사용처에 미치는 영향과 주요 설계 판단
- 수정한 파일
- 실행한 테스트와 실제 결과
- 업데이트한 명세·문서
- 실행하지 못한 검증과 이유
- 남은 위험과 사용자 판단 항목

검증하지 않은 결과를 통과했다고 보고하지 않는다.
